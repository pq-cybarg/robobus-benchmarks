kafka · protocol vs library

Kafka the protocol, not the library

The Transports table above measures robobus moving a frame through a real Kafka broker (durable, acks=1, cross-broker replicated), the honest cost of Kafka's strongest guarantee. But Kafka is a wire protocol, and robobus speaks it directly: it emits and parses the exact Kafka RecordBatch v2 bytes a standard client reads (CRC and all), so it can interpret the protocol itself, skip the JVM and the client, and provide the durable, replayable feature far faster, with per-message post-quantum AES-256-GCM Kafka does not have. The Kafka-core encoder + durable log is ported to four native languages, every port byte-for-byte identical to the Python reference (checked against kafka-python). web · browser platform · WebCrypto + WASM · CNSA 2.0

The web is a first-class platform

The 34th ecosystem is the browser itself , and it is local-first: the case where you cannot defer to a server's AES-NI, so maximum in-browser capability is the whole point. The exact post-quantum-class sealed Kafka RecordBatch is produced in a real browser (headless-verified), byte-identical to libkafcore. Two routes: WebCrypto AES-256-GCM (SubtleCrypto, real hardware AES-NI, but async , one promise per call), and a WASM build carrying an audited software AES (AWS-LC aes_nohw, unmodified, ISC / FIPS-lineage, constant-time bitsliced , the same audited-COTS rule as the rest of the stack), synchronous with no async boundary. The key insight is two regimes: small messages are a rate game, bulk is a bandwidth game, and each route wins one.

Small, high-rate messages , the WASM path wins. WebCrypto's async round-trip dominates a tiny record, so the synchronous audited software AES pulls ahead: ~1.2M seals/s at 32 B, single-thread (the two routes cross near 4 KB, where WebCrypto's hardware AES starts to matter more than its async cost). WebAssembly has no AES-NI, so this is software AES , excellent for message rate, but it caps ~113 MB/s of bandwidth. Best-of-3, machine-measured.

transport × language · the full product

Every language, every transport

The complete grid: each of 26 languages driving each of 12 transports with the real 75-byte sealed frame (frames/s, loopback). The three socket transports (UDP/TCP/UDS) each language drives with its own native BSD sockets, or libc sockets via C interop for Fortran/Nelua/Pascal/COBOL/Mojo. The broker & middleware rows (SHM, Serial, CAN, MQTT, AMQP, DDS, ZeroCM, LSL, marked ·shim) have no native per-language client, so every language reaches them the same way the crypto matrix reaches a missing primitive: through one labeled C shim (librbxport) wrapping each transport's real C library (libmosquitto, rabbitmq-c, CycloneDDS, libzcm, liblsl, plus an in-C virtual CAN bus and POSIX shm/pty), called through the language's own FFI. Read those rows by row: the transport work happens in shared C, so within a row languages converge (the FFI overhead is nearly free) and the spread is run-to-run noise on a shared host, not language speed. The transport sets the ceiling, not the caller. The one exception is Kafka (marked ·native): robobus speaks the Kafka wire protocol itself (demos/kafka-protocol), so this row is the native protocol produce path, AES-256-GCM seal + Kafka RecordBatch v2 encode per message in each language's own loop over the C ABI, not an external-broker round-trip. That work is caller-bound, so the Kafka row spreads by language like the codec table (3M peak) instead of converging, and it runs on the order of 100x to 200x the old librdkafka broker round-trip (~15k) it replaces. Colour is log-scaled; the grid runs from SHM (~74M f/s, an in-process ring) down to LSL (~100k), about 4,851x top to bottom. Every cell is filled, all 26 languages × 12 transports, zero blanks. Where a language ships no native socket client (TCP/UDS in the JVM, Node, Lua, Mojo, Octave…) it reaches the socket through the same shim's UDP/TCP/UDS path. The crypto matrix

robobus carries a whole crypto suite, not one cipher, so this is the complete grid: every one of the 26 primitives it uses (AEAD ciphers, SHA-2/SHA-3/BLAKE3 hashes, Argon2id/scrypt/PBKDF2/HKDF/KMAC KDFs, the ML-KEM and X25519 KEMs, and the ML-DSA/SLH-DSA/Falcon and Ed25519 signatures) timed in every one of the 34 language configs, grouped per technique so each bar chart is a coherent apples-to-apples comparison (identical workload, ranked fastest first). Pick whichever primitives your requirements call for; the configurator at the top of the page reports which compliance regime (FIPS, CNSA 2.0, CSfC, NIST level) any given selection satisfies. Each language uses its native-maximum stack where it has one (stdlib, CryptoKit/JCE, RustCrypto, OpenSSL via its own FFI); where a language has no native implementation it reaches the primitive through one labeled C shim over OpenSSL 3.6.3 + liboqs + libblake3, so no cell is empty. The KEM and signature groups also carry the distinct backends (OpenSSL EVP, liboqs, Go's native crypto/mlkem) for an implementation-quality comparison. Argon2id is known-answer-verified in every language.

Pick your requirement, see the cost

Security is a spectrum you choose per link, not a mandate, from classical (backwards-compatible with non-PQ peers) through hybrid transition profiles to CNSA 2.0 for National Security Systems. Each profile splits into two cost centres: session setup (the ML-KEM / ML-DSA handshake, once per peer, amortized) and the per-message hot path (AES-256-GCM, every frame). Session cost swings ~130× with assurance; per-message stays flat at line rate, so higher security buys handshake latency, not throughput.
